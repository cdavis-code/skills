# PointAndProof MCP tool reference

Every tool maps one-to-one onto an HTTP route in the PointAndProof API, so the same
validation, credit rules, and state gates apply in a harness as in the web app.
The workflows, the human-in-the-loop contract, and the two starting points
(from an article, from the expert's brief) live in [`../SKILL.md`](../SKILL.md).

## Tool contracts (25 tools)

- `create_run(article_url?, perspective?, generate_image?, force_review=True, allow_duplicate?, expertise_brief?)` returns `{run_id, status}`. Three modes: topic discovery (no `article_url`), source mode (`article_url`), and expertise mode (`article_url` plus `expertise_brief` = `{"kind": ..., "fields": {...}}`). Expertise mode takes no `perspective` — the brief kind is the structural authority and the API refuses a take alongside a brief ("Use the expertise brief or a take, not both."). Expertise runs always pause for approval and have no article-selection pause. `generate_image` defaults to no image regardless of the tenant's preference — pass `true` only when the user asked for one up front; otherwise gather consent at the approval checkpoint. `allow_duplicate` republishes a source used within the last 60 days — use it only after the refusal below and the user's explicit agreement. Maps to `POST /runs`.
- `discover_sources_for_brief(expertise_brief)` returns `{candidates: [...], cached}`, each candidate carrying `url`, `title`, `score` (brief fit), `relationship` (`supports` / `challenges` / `related`), `reason`, `source`, `scored`, and `publish_date`. Best-effort search over recent articles; creates no run and spends no post credit. Only individual verified articles come back — homepages, category/archive/search pages, feeds, digests, and pages with no checkable publication date are filtered out, so a short or empty list means nothing citable was found, not that the brief is wrong. Present the candidates and let the user pick — this is a choice, not an auto-pick. On "Source search failed. Please try again." or an empty list, ask for a URL and continue with `create_run`. Maps to `POST /articles/discover` with `{"expertise_brief": ...}`.
- `select_source(run_id, candidate_id, perspective?)` returns `{run_id, ok, status}`. A source the article policy refuses answers 409 with "That source is not a verified article", "...outside the freshness window for your topics", or "That page is a section or listing, not an article" — offer another candidate or a rediscover, and never retry the same id. Maps to `POST /runs/{run_id}/select-article`.
- `get_run(run_id?)` returns `{active: <run>|null}` without arguments (the tenant's live run), or the full run record — `status`, article fields, `draft_body`, validation notes, and `expertise_brief` on expertise runs — with a run id. A `succeeded` record carries `post_url` (the published LinkedIn permalink — present it as proof); a `failed` record carries `error` and `error_kind` (quote them verbatim). Maps to `GET /runs/active` and `GET /runs/{run_id}`.
- `check_claims(run_id, draft_body?)` returns the parked draft's claims against the selected source — each with `text`, `verdict`, `passage`, `passage_text`, `basis` (`source` or `brief`), and `brief_field` for brief claims. `verdict: "from_brief"` means the claim restates the author's own practice observation and was not checked against the source. `basis_available: false` means the split failed and every claim was compared with the source. Pass `draft_body` after edits; omit it to use the stored draft. Paid plans only. The verdicts are stored with the text they were computed from, so editing the draft afterwards marks the check stale; whether an unresolved contradiction blocks the send depends on the deployment's gate, and acknowledging one happens in the web app, not here. Maps to `POST /runs/{run_id}/claim-check`.
- `list_candidates(run_id)` returns `{candidates: [...]}` (id, url, title, score, used, rejected, topic, publish_date, plus `eligibility_state`, `eligibility_reasons`, `freshness_state`, and `freshness_reason` when the run computed them), best-scored first. Policy-refused rows arrive with `rejected: true` and their reason and cannot be drafted from, so present them as unavailable rather than as a choice. Maps to `GET /runs/{run_id}/candidates`.
- `cancel_run(run_id)` returns `{ok}`; deletes the run and frees the single-active-run slot. Maps to `POST /runs/{run_id}/cancel`.
- `get_draft_options()` returns the shaping context: `voice_profiles` (id, name, source_type, active flag, sample_count, editorial_preferences), `default_take`, `saved_takes`, and `expertise_brief` (`kinds` with slug, label, description and the two kind-specific fields; `common_fields` with key, label, question, max_chars). Call it before every `create_run`.
- `suggest_takes(article_url)` returns `{suggestions: [...]}` — three article-derived angles (one small LLM call; creates no run, spends no credit; empty list when the article can't be read). Maps to `POST /articles/suggest-takes`.
- `approve_draft(run_id, edited_body?, include_image?, publish_mode?, publish_at?, save_as_sample?)` returns `{ok, ...}`. An approval the send guards refuse is answered on the spot with the reason (over LinkedIn's character limit, a source claim the check contradicts and nobody acknowledged, or a check made stale by the edit): nothing is written, the run stays at `awaiting_approval`, so fix the draft (or re-run `check_claims`) and approve again. Without `publish_at` it records the approval and publishing starts — the reply is **not** proof the post is live (the credit is spent only when the publish succeeds), so verify with `get_run` (approval checkpoint step 7). With `publish_at` (ISO 8601 with an offset) the draft is parked instead and publishes at that instant; the reply is `{"publication": "scheduled", "scheduled_publish_at"}` — confirm the time and do not poll. `include_image=False` drops the AI image; windowed runs must pass `publish_mode="scheduled"` (queue) or `"now"`. `save_as_sample=true` explicitly adds the final text to the active custom voice; pass it only when the user says the draft sounds like their writing. Requires the tenant's voice-learning opt-in; no effect on preset profiles. Maps to `POST /runs/{run_id}/approve`.
- `edit_draft(run_id)` offers the draft in a pre-filled pop-up edit form (elicitation) where supported; pass the returned `edited_body` to `approve_draft`. Returns `{"supported": false}` immediately on today's hosted transport (the pop-up needs a stateful transport) — use the file or chat layers of the approval checkpoint. `{"cancelled": true}` means the user backed out.
- `generate_image(run_id)` generates the post's image the first time or regenerates it afterwards (only with explicit opt-in — paid feature; trials are refused with the API's own message). Returns `{ok, remaining}`; the reply's `remaining` is what the web shows as "Generate alternate (N left)". Maps to `POST /runs/{run_id}/regenerate-image`.
- `get_image(run_id)` returns the generated PNG as image content so the harness can display it. Errors distinguish "No image is requested" (offer `generate_image` first) from "still generating" (retry in a few seconds). Maps to `GET /runs/{run_id}/image`.
- `list_voice_profiles()` returns `{profiles: [...]}` — id, name, source_type, status, sample_count, analysis_version, editorial_preferences per profile. Maps to `GET /voice/profiles`.
- `get_voice_profile(profile_id)` returns the full profile incl. `editorial_preferences`, `samples` (sanitized previews only — stored raw text never leaves the server), and `latest_analysis`. Maps to `GET /voice/profiles/{id}`.
- `create_voice_profile(name, source_type?, preset_key?, explicit_user_instructions?, do_not_use_instructions?, editorial_preferences?)` returns the created profile. `source_type="preset"` needs `preset_key` and activates immediately; `"manual"`/`"samples"` start as drafts. Maps to `POST /voice/profiles`.
- `update_voice_profile(profile_id, name?, explicit_user_instructions?, do_not_use_instructions?, generated_style_guide?, status?, example_selection_strategy?, editorial_preferences?)` — patch semantics; `editorial_preferences` replaces the whole preference object; `status` is `draft`/`archived` only (use `activate_voice` to activate). Maps to `PATCH /voice/profiles/{id}`.
- `add_writing_sample(profile_id, text, sample_kind?, user_label?, is_pinned?)` — text 100–8,000 chars, sanitized before storage and analysis; duplicate texts and an 11th sample are refused. Maps to `POST /voice/profiles/{id}/samples`.
- `update_writing_sample(sample_id, user_label?, is_pinned?, is_active?)` — pin, deactivate (kept but out of play), or relabel. Maps to `PATCH /voice/samples/{id}`.
- `analyze_voice(profile_id)` returns the fresh analysis incl. `style_guide`; present it with the sample previews and ask whether it sounds like the user before activating. Needs ≥3 active samples; 6 per hour per tenant. Maps to `POST /voice/profiles/{id}/analyze`.
- `activate_voice(profile_id)` returns the activated profile; archives the previously active one. Its voice and editorial preferences apply to every future draft, in either mode. Maps to `POST /voice/profiles/{id}/activate`.
- `delete_writing_sample(sample_id)` returns `{ok: true}`; permanent, with no restore. Maps to `DELETE /voice/samples/{sample_id}`.
- `delete_voice_profile(profile_id)` returns `{ok: true}`; permanent (the profile delete cascades to its samples and analyses). Maps to `DELETE /voice/profiles/{profile_id}`.
- `get_schedule()` returns the recurring publishing schedule — `{configured: false}` when none exists — with `enabled`, `frequency`, `days_of_week`, the window fields, `timing_mode`, `timezone` (the tenant's display timezone), `next_run_at`, image/platform options. Maps to `GET /schedules?version=2`.
- `set_schedule(enabled, frequency, hour, minute, day_of_week?, days_of_week?, end_hour?, end_minute?, confirmation_email_enabled?, generate_image?, target_platforms?)` creates or replaces that schedule. Enabling needs a paid plan; a window must be sent complete; on an auto-approve tenant it publishes without review. Maps to `PUT /schedules`.

## Scopes

Scopes apply per tool: `get_run`, `list_candidates`, `get_draft_options`,
`edit_draft`, `get_image`, `get_schedule`, `list_voice_profiles`, and
`get_voice_profile` work with any token (including `read-only`); `suggest_takes`,
`check_claims`, `create_run`, `discover_sources_for_brief`, `select_source`,
`cancel_run`, `generate_image`, and all eight voice writes
(`create_voice_profile`, `update_voice_profile`, `add_writing_sample`,
`update_writing_sample`, `analyze_voice`, `activate_voice`,
`delete_writing_sample`, `delete_voice_profile`) need `draft-only` or `full` —
`draft-only` tokens can never publish. `approve_draft` requires `full`: it is the
publish gate. `set_schedule` also requires `full` — enabling a recurring schedule
on an auto-approve tenant publishes without review, so a draft-only token must
not be able to do it. Refusals name the scope in the error. An OAuth-issued
token carries the same ladder: the consent page offers `draft-only` by default
and `full` as the opt-in, and the token it mints is listed and revoked beside
the pasted ones.
